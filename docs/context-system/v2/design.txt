CONTEXT SYSTEM v2 - Design
==========================

PURPOSE
-------
Assemble dynamic context for LLM prompts based on:
- Cumulative gates (checkpoints that unlock content)
- Persistent traits (user characteristics that branch content)
- Fluid modes (current conversational focus)
- Per-message signals (detected intent/events)
- Priority-ordered rules


WHY 4 EXTRACTION PRIMITIVES?
----------------------------

The 4 state primitives form a 2x2 matrix across two dimensions:
- Persistence: permanent vs fluid
- Type: state (what IS) vs event (what HAPPENED)

                    | State (what IS)  | Event (what HAPPENED)
--------------------|------------------|----------------------
Permanent           | TRAIT            | GATE
Fluid               | MODE             | SIGNAL

- TRAIT = permanent state → who the user IS (skill_level, use_case)
- GATE  = permanent event → what HAS happened (interest_confirmed, link_sent)
- MODE  = fluid state → where we ARE now (discovery, objection_handling)
- SIGNAL = fluid event → what JUST happened (intent: objection)

This is the minimal complete set. Can't reduce without losing information.


PRIMITIVES
----------

1. GATE
   A checkpoint that gets set and stays set. Controls what content is allowed.
   - id: string
   - name: string
   - required_for: [labels]            # what this gate unlocks
   - enforcement: "hard" | "soft"      # hard = blocked, soft = gather naturally

2. TRAIT
   A user characteristic detected early, persists throughout, branches content.
   - id: string
   - name: string
   - type: enum | string
   - options: string[] (if enum)
   - detection_hint: string            # helps LLM extract this

3. MODE
   Current conversational focus. Shifts per-message based on signals.
   - id: string
   - name: string
   - default_labels: [labels]          # what to inject when in this mode

4. SIGNAL
   Per-message detection. Ephemeral, triggers reactions.
   - id: string
   - name: string
   - type: enum | string | boolean
   - options: string[] (if enum)
   - detection_hint: string

5. RULE
   Condition → Assembly Action logic for context assembly.
   - id: int
   - priority: int                     # lower = higher priority
   - name: string
   - enabled: boolean
   - conditions: Condition[]
   - assembly_action: AssemblyAction   # inject/search/block
   - mode_shift: mode_id (optional)    # shift mode when rule fires

6. CHUNK
   A piece of content with labels and optional trait filtering.
   - id: int
   - labels: [string]                  # flexible categorization (many labels per chunk)
   - title: string (optional)
   - content: text
   - trait_filter: {trait_id: value}   # optional, filters by user traits
   - token_count: int
   - embedding: vector

7. TOOL
   An executable action the agent can take.
   - id: string
   - name: string
   - requires_gates: [gate_ids]        # must be unlocked to use
   - confirmation_required: boolean    # ask user before executing


CONDITION FORMAT
----------------

{
  operator: "AND" | "OR",
  clauses: [
    {field: "gate.interest_confirmed", op: "==", value: true},
    {field: "trait.skill_level", op: "==", value: "zero"},
    {field: "signal.intent", op: "==", value: "objection"},
    {field: "mode", op: "==", value: "discovery"}
  ]
}

Special condition: {operator: "always"} - always fires


ASSEMBLY ACTION FORMAT
----------------------

Inject (deterministic):
{type: "inject", labels: ["stage:descoberta", "objection"]}

Search (semantic/RAG):
{type: "search", labels: ["objection"], limit: 3, query: "last_message" | "signal.objection_type"}

Block (remove):
{type: "block", labels: ["pricing", "link"]}


ENTITY RELATIONS
----------------

AGENT (1)
  │
  ├──< GATE (N)
  │
  ├──< TRAIT (N)
  │
  ├──< MODE (N)
  │
  ├──< SIGNAL (N)
  │
  ├──< RULE (N)
  │      └── references: gates, traits, modes, signals, labels
  │
  ├──< CHUNK (N)
  │      └── has: labels[], trait_filter, embedding
  │
  └──< TOOL (N)
         └── references: gates

PIPELINE STAGES
---------------

1. EXTRACT
   - Input: last message + history
   - Output: signals, trait updates, gate updates, mode shift
   - Actor: LLM

2. ASSEMBLE
   - Input: state + rules
   - Output: context chunks
   - Actor: Deterministic + RAG
   - Steps:
     a. Evaluate rules in priority order
     b. For each firing rule: inject/search/block by labels
     c. Filter chunks by trait_filter (match current traits)
     d. Filter by gate requirements (hard/soft enforcement)
     e. Dedupe chunks
     f. Trim to token budget (prioritize by rule priority)

3. GENERATE
   - Input: context + history + state
   - Output: response text + tool decisions
   - Actor: LLM

4. VALIDATE
   - Input: response
   - Output: validated response
   - Actor: Rules/LLM
   - Checks: never_say rules, constraint violations

5. EXECUTE
   - Input: tool decisions
   - Output: tool results, gate updates
   - Actor: Tools

6. FORMAT
   - Input: response
   - Output: final message(s)
   - Actor: Deterministic
   - Applies: multi-turn splitting, style rules


GATE TRANSITIONS
----------------

Gates are set when certain conditions are detected:

name_captured:
  when: traits.customer_name != null

skill_identified:
  when: traits.skill_level != null

need_identified:
  when: traits.use_case != null

interest_confirmed:
  when: signal.intent == "agreement" | "ready_to_buy"
  OR: explicit phrases like "quero aprender", "faz sentido"

link_offered:
  when: tool "offer_link" was executed

link_sent:
  when: tool "send_link" was executed

purchased:
  when: signal.intent == "purchased"
  OR: user confirms purchase


MODE TRANSITIONS
----------------

Modes shift fluidly based on signals:

discovery → validation:
  when: gate.skill_identified AND gate.need_identified

validation → objection_handling:
  when: signal.intent == "objection"

objection_handling → validation:
  when: signal.intent == "agreement" (objection resolved)

validation → presentation:
  when: gate.interest_confirmed

presentation → closing:
  when: signal.intent == "ready_to_buy"

closing → nurturing:
  when: signal.intent == "objection" AND repeated

any → fallback:
  when: signal.intent == "other" | "unclear"


TOKEN BUDGET
------------

Default: 2000 tokens for context

Allocation by rule priority:
- Priority 1-5: guaranteed (up to 800 tokens)
- Priority 6-20: best effort (up to 800 tokens)
- Priority 21+: only if space remains

If over budget:
1. Truncate lowest-priority chunks first
2. Reduce search limits
3. Never truncate priority 1-3


UI SCREENS
----------

1. OVERVIEW
   - Agent name, description, personality
   - Quick stats: gates, traits, modes, rules, chunks

2. GATES
   - List of checkpoints
   - For each: name, required_for labels, enforcement toggle
   - Visual: which gates unlock which content

3. TRAITS
   - List of user characteristics
   - For each: name, type, options, detection hint

4. MODES
   - List of conversational focuses
   - For each: name, default labels
   - Visual: mode transition diagram

5. SIGNALS
   - List of per-message detections
   - For each: name, type, options, detection hint

6. RULES
   - Priority-ordered list (drag to reorder)
   - For each: conditions builder, assembly action selector, mode shift
   - Enable/disable toggle

7. CONTENT (Chunks)
   - Chunk list with label filters
   - For each: content, labels (editable), trait_filter
   - Upload with AI-suggested labels
   - Manual add

8. TOOLS
   - List of executable capabilities
   - For each: name, required gates, confirmation toggle

9. SIMULATOR
   - Input: customer message
   - State editor (gates, traits, mode)
   - Output: extracted signals, rules fired, context assembled, response
