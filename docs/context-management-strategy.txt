USER REQUESTS → LANGGRAPH IMPLEMENTATION GUIDE
==============================================

This document maps what users say in plain language to how we implement it with LangGraph.
Every feature stems from real use cases (see: use-cases-real-world.txt)

**LAST UPDATED:** 2025-11-02 - After móveis agent implementation


CRITICAL LEARNINGS (TL;DR)
--------------------------

1. **LangGraph is a library, NOT a server** - Runs in-process with our FastAPI backend
2. **response_schema does double duty** - Generates both LangGraph TypedDict AND OpenAI extraction schema
3. **State updates must return dicts** - Nodes return `{"field": value}`, don't mutate state directly
4. **Tool calling ≠ state tracking** - Tools loop via graph edges, not via response_schema flags
5. **Missing Actions node** - Need explicit node between Generate Response and Validate for tool execution
6. **Graph factory per agent** - Each agent gets compiled graph, cached in memory, rebuilt when schema changes
7. **LangGraph manages persistence** - PostgreSQL checkpointer auto-saves state, we don't manually save/load
8. **UI nodes map to config** - TrackingNode → response_schema, KnowledgeNode → gating_rules, etc.
9. **No universal schema trap** - Each agent has exactly the fields it needs, dynamically generated
10. **Users never see LangGraph** - All complexity abstracted behind simple UI and conversation


ARCHITECTURE: LangGraph as Library
-----------------------------------

**CRITICAL: LangGraph is NOT a server.** It's a Python library that runs in-process with FastAPI.

```python
from langgraph.graph import StateGraph  # Just a library import

graph = create_graph_for_agent(agent_config)  # Compile in-process
result = graph.invoke(state)  # Execute directly in FastAPI
```

**No separate LangGraph server needed.** Our FastAPI backend IS the server.
**Optional servers exist** (LangGraph Studio, LangServe) but we don't need them.


CORE PRINCIPLE: Fixed Pipeline, Flexible Rules
-----------------------------------------------

**Users DON'T build graphs.** They talk to an AI manager, upload docs, describe behavior.
**We build ONE graph** that works for everyone. Only the rules/data change.

**Fixed LangGraph Pipeline:**
Extract State → Apply Gating → RAG Search → Generate Response → Execute Actions → Validate

**What Users Configure (via chat):**
- Knowledge (upload PDFs, describe what AI should know)
- State fields (what to track: budget, urgency, sentiment)
- Gating rules (when to hide/show certain knowledge)
- Tone & language (professional, friendly, emojis yes/no)
- Actions/Tools (calendar, payments, database)
- Validation rules (safety checks)
- Handoff triggers (when to escalate to human)


RESPONSE_SCHEMA: Dual Purpose
------------------------------

**response_schema is the single source of truth** for agent behavior.

**Stored in DB (Agent model):**
```json
{
  "budget_range": ["unknown", "under_5k", "5k_to_20k", "20k_plus"],
  "lead_quality": ["browser", "warm", "hot"],
  "urgency": ["normal", "urgent", "emergency"]
}
```

**Two uses from ONE config:**

1. **Generates LangGraph TypedDict** (compile time):
   ```python
   class AgentState(TypedDict):
       messages: List[dict]
       budget_range: Optional[str]
       lead_quality: Optional[str]
       urgency: Optional[str]
   ```

2. **Generates OpenAI Extraction Schema** (runtime):
   ```python
   extraction_schema = {
       "type": "object",
       "properties": {
           "budget_range": {"type": "string", "enum": ["unknown", "under_5k", ...]},
           "lead_quality": {"type": "string", "enum": ["browser", "warm", "hot"]},
           ...
       }
   }
   ```

**No translation needed.** Same schema, two outputs.
**User edits in UI** → updates DB → regenerates both schemas → recompiles graph.

IMPLEMENTATION GOTCHAS (Critical Lessons)
-----------------------------------------

### 1. State Updates Must Return Dicts
**❌ WRONG:**
```python
def apply_gating_node(state: AgentState) -> AgentState:
    state["excluded_tags"] = ["pricing"]  # Mutation doesn't work!
    return state
```

**✅ CORRECT:**
```python
def apply_gating_node(state: AgentState) -> dict:
    return {"excluded_tags": ["pricing"]}  # Return updates as dict
```

LangGraph merges returned dicts into state. Direct mutation is invisible.

### 2. All State Fields Must Be Declared in TypedDict
Even internal processing fields (excluded_tags, rag_context, validation_passed) must be in the TypedDict.
LangGraph won't accept fields that aren't declared in schema.

### 3. Tool Calling ≠ State Tracking
- **State fields** (response_schema): Business logic tracking (budget, urgency)
- **Tool calling**: Handled by graph edges + OpenAI function calling
- Don't mix them. Tools loop via conditional edges, not state flags.

### 4. Graph Compilation is Per-Agent
Each agent gets its own compiled graph instance, cached in memory.
When user updates response_schema → invalidate cache → recompile graph.

### 5. LangGraph Manages State Persistence
With PostgreSQL checkpointer, LangGraph automatically:
- Saves state after each node
- Loads state at start of each turn
- Enables conversation branching/rollback
We don't manually save/load state.

THE LANGGRAPH THAT GETS GENERATED
----------------------------------

## Dynamic State Schema (Per-Agent)

**Each agent gets its own StateGraph** with a dynamically generated schema based on `response_schema`.

**Graph Factory Function:**
```python
def create_agent_state(agent_id: str, response_schema: dict):
    """
    Dynamically creates TypedDict from agent's response_schema.

    Example response_schema:
    {
        "urgency": ["normal", "urgent", "emergency"],
        "issue_type": ["question", "booking", "emergency"],
        "location_preference": ["location_1", "location_2", "location_3", "any"]
    }
    """
    # Core fields (always present)
    fields = {
        "messages": List[Message],  # Required by LangGraph
    }

    # Add agent-specific fields from response_schema
    for field_name in response_schema.keys():
        fields[field_name] = Optional[str]  # All tracking fields are optional strings

    # Dynamically create TypedDict class
    StateClass = TypedDict(f'AgentState_{agent_id}', fields)
    return StateClass


def create_graph_for_agent(agent_config):
    """Creates a compiled graph instance for a specific agent."""
    # 1. Generate state schema
    StateClass = create_agent_state(agent_config.id, agent_config.response_schema)

    # 2. Build graph with fixed pipeline
    graph = StateGraph(StateClass)

    # Add nodes (same for all agents)
    graph.add_node("extract_state", extract_state_node)
    graph.add_node("apply_gating", apply_gating_node)
    graph.add_node("rag_search", rag_search_node)
    graph.add_node("generate_response", generate_response_node)
    graph.add_node("validate", validate_node)
    graph.add_node("handoff", handoff_node)
    # Tools added conditionally based on agent_config.tools

    # Add edges (same for all agents)
    graph.add_edge("extract_state", "apply_gating")
    graph.add_edge("apply_gating", "rag_search")
    graph.add_edge("rag_search", "generate_response")
    graph.add_edge("generate_response", "validate")

    # Conditional edges (rules from agent_config)
    graph.add_conditional_edges("validate", route_after_validation)

    # 3. Compile with checkpointer
    checkpointer = PostgresCheckpointer(connection_string)
    return graph.compile(checkpointer=checkpointer)
```

**Runtime Management:**
```python
# Cache of compiled graphs per agent
compiled_graphs: Dict[str, CompiledGraph] = {}

def get_graph_for_agent(agent_id: str):
    """Gets or creates compiled graph for agent."""
    if agent_id not in compiled_graphs:
        agent = db.get_agent(agent_id)
        compiled_graphs[agent_id] = create_graph_for_agent(agent)
    return compiled_graphs[agent_id]

def update_agent_schema(agent_id: str, new_response_schema: dict):
    """Updates agent's schema and rebuilds graph."""
    # 1. Update database
    agent = db.get_agent(agent_id)
    agent.response_schema = new_response_schema
    db.save(agent)

    # 2. Rebuild graph with new schema
    compiled_graphs[agent_id] = create_graph_for_agent(agent)

    # Note: Existing conversations keep old schema (checkpointed state)
    # New conversations use new schema
```

KEY PRINCIPLES (Updated)
------------------------

1. **LangGraph is a library** - Runs in-process with FastAPI, not a separate server
2. **Users talk, we implement** - No graph building, just conversation with AI manager
3. **One graph structure, dynamic schema** - Fixed 6-node pipeline, per-agent state fields
4. **response_schema is dual-purpose** - Generates both TypedDict AND OpenAI extraction schema
5. **State drives everything** - Schema fields control flow, extracted every turn
6. **Graph factory pattern** - Each agent gets compiled graph instance, cached in memory
7. **Schema updates rebuild graph** - UI changes trigger graph regeneration via cache invalidation
8. **State updates return dicts** - Nodes return state updates, don't mutate directly
9. **Gating = smart filtering** - Show/hide knowledge based on state via tag exclusion
10. **Tool calling via graph edges** - Not via response_schema flags, handled by conditional routing
11. **Actions node is critical** - Between Generate Response and Validate, handles tool execution loop
12. **LangGraph manages persistence** - PostgreSQL checkpointer handles state save/load automatically
13. **Visual nodes = educational** - Dashboard shows configuration, not construction tool
14. **All complexity abstracted** - Users never see TypedDict, StateGraph, or LangGraph terminology

**Bottom Line:**
Users get a WhatsApp assistant in 20 minutes by talking and uploading files.
We get enterprise-grade orchestration with LangGraph under the hood.
Each agent tracks exactly what it needs via dynamic schemas - no universal schema trap.
Win-win.
