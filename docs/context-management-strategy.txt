USER REQUESTS → LANGGRAPH IMPLEMENTATION GUIDE
==============================================

This document maps what users say in plain language to how we implement it with LangGraph.
Every feature stems from real use cases (see: use-cases-real-world.txt)


CORE PRINCIPLE: Fixed Pipeline, Flexible Rules
-----------------------------------------------

**Users DON'T build graphs.** They talk to an AI manager, upload docs, describe behavior.
**We build ONE graph** that works for everyone. Only the rules/data change.

**Fixed LangGraph Pipeline:**
Extract State → Apply Gating → RAG Search → Generate Response → Validate → Tools/Handoff

**What Users Configure (via chat):**
- Knowledge (upload PDFs, describe what AI should know)
- State fields (what to track: budget, urgency, sentiment)
- Gating rules (when to hide/show certain knowledge)
- Tone & language (professional, friendly, emojis yes/no)
- Handoff triggers (when to escalate to human)
- Tools (calendar, payments, database)
- Validation rules (safety checks)


PATTERN 1: KNOWLEDGE - "The AI Should Know..."
-----------------------------------------------

### What Users Say
- "Know our prices for different visa types" (PDF)
- "Know what documents are needed" (PDF)
- "Explain what each course covers" (descriptions)
- "Send our menu" (PDF with photos)
- "Has list of insurance plans we accept" (document)
- "Knows our price table" (structured data)

### How We Implement
**LangGraph Node:** RAG Search Node
**Technology:** Embeddings + Vector DB with tags

**Process:**
1. User uploads PDF/documents in chat
2. Backend chunks, embeds, stores in vector DB
3. Each chunk gets tags (e.g., "pricing", "procedures", "products")
4. RAG node searches filtered by tags (gating controls which tags)

**Example:**
User: "Upload your price list"
→ Backend processes PDF
→ Creates knowledge blocks with tag: "pricing"
→ RAG node can search this when needed

**Visual Nodes Impact:**
→ KnowledgeNode shows: "3 blocos" (3 knowledge blocks uploaded)


PATTERN 2: STATE TRACKING - "I Need to Know..."
------------------------------------------------

### What Users Say
- "Qualify their budget before showing prices"
- "Mark dental emergencies as URGENT"
- "Check if they're a beginner or advanced"
- "Detect if customer is frustrated/angry"
- "Track if payment went through"
- "Know which insurance plan they have"

### How We Implement
**LangGraph:** AgentState schema (StateGraph state)
**Technology:** OpenAI structured outputs

**Process:**
1. User describes what to track: "I need to know their budget range"
2. AI manager adds to response_schema: `budget_range: ["unknown", "under_5k", "5k_to_20k", "20k_plus"]`

4. State flows through entire graph

**Common State Fields:**
```
budget_range: ["unknown", "low", "medium", "high"]
urgency: ["normal", "urgent", "emergency"]
sentiment: ["neutral", "positive", "frustrated", "angry"]

issue_type: ["question", "complaint", "booking", "technical"]
language_detected: ["pt", "en"]
insurance_type: ["covered", "not_covered", "unknown"]
experience_level: ["beginner", "intermediate", "advanced"]
```

**Example:**
User: "If someone has a dental emergency, mark as URGENT"
→ response_schema gets: `urgency: ["normal", "urgent", "emergency"]`
→ Extract State node detects keywords: "pain", "broken tooth" → sets urgency = "emergency"
→ Conditional edge: if urgency == "emergency" → route to handoff node

**Visual Nodes Impact:**

PATTERN 3: GATING - "Don't Show... Until..."
---------------------------------------------

### What Users Say
- "Don't show prices until I know their budget"
- "NEVER give legal advice, just info about our services"
- "If budget is low, don't waste time on premium products"
- "Only show gluten-free options if they mention allergies"

### How We Implement
**LangGraph:** Conditional edge before RAG node
**Technology:** Tag-based filtering

**Process:**
1. User describes condition: "Don't show prices until budget is known"
2. AI manager creates gating_rule: `{if: "budget_range == 'unknown'", exclude_tags: ["pricing"]}`
3. Apply Gating node reads state, applies filters
4. RAG node only searches allowed tags

**Example:**
Law firm: "NEVER give legal advice"
→ gating_rule: `{exclude_tags: ["legal_advice"]}`
→ Knowledge tagged "legal_advice" is NEVER retrieved

Dental: "Don't show prices if insurance covers"
→ gating_rule: `{if: "insurance_type == 'covered'", exclude_tags: ["pricing"]}`
→ If insurance covers, pricing docs hidden from RAG

**Visual Nodes Impact:**
→ FilterNode appears attached to KnowledgeNode
→ Shows: "2 regras" (2 gating rules active)

- "If technical problem AI can't solve, email me"

### How We Implement

**Technology:** Sentiment extraction + notification integrations

**Process:**
1. User describes handoff trigger
2. AI manager adds to state schema (e.g., requires_handoff, handoff_reason)
3. Extract State node detects trigger conditions
4. Conditional edge routes to Handoff node

```

urgency == "emergency" → handoff (reason: "emergency", urgent=true)
issue_type == "complaint" → handoff (reason: "complaint")
requires_legal_advice == true → handoff (reason: "needs expert")
problem_too_complex == true → handoff (reason: "complex issue")
wants_cancellation == true → handoff (reason: "retention needed")
unethical_request == true → decline & stop conversation
```

**Notification Channels:**
- Slack webhook
- Email alert
- WhatsApp message to owner
- Dashboard notification

**Example:**
Restaurant: "If complaint about food, notify me and get owner"
→ Extract State detects: "complaint" + "food quality" → requires_handoff=true, handoff_reason="complaint"
→ Conditional edge: if requires_handoff → route to Handoff node
→ Handoff node: sends Slack alert + tells customer "Let me get the owner"

PATTERN 8: VALIDATION - "Don't Let AI..."
------------------------------------------

### What Users Say
- "Only take simple orders - if complex, connect with team"
- "If severe allergy, recommend calling chef"
- "Don't promise things we can't deliver"
- "If mentions competitor, don't badmouth - stay professional"

### How We Implement
**LangGraph Node:** Validation node + retry edge
**Technology:** Post-generation checks (regex, keyword, or LLM validation)

**Process:**
1. User describes constraint: "Don't take complex orders"
2. AI manager creates validation_rule
3. Generate Response produces output
4. Validation node checks rules
5. If fails → retry (max 2 attempts) or escalate

**Common Validation Rules:**
```
Response mentions competitor → rewrite to stay neutral
Response promises impossible deadline → strip promise
Response too long (>3 sentences) → shorten
Response contains prices but budget unknown → strip prices
Order is complex (>3 items with modifications) → handoff instead
```

**Example:**
Restaurant: "Only simple orders - if complex, handoff"
→ User: "I want 2 pizzas, one with no cheese, extra olives, and can you add grilled chicken, plus a pasta with..."
→ Validation detects: order_complexity = "high"
→ Validation fails → rewrites to: "This sounds like a special order! Let me connect you with our team to get it just right."

Law firm: "Never give legal advice"
→ Response: "You should file within 30 days"
→ Validation detects: giving_legal_advice = true
→ Validation fails → rewrites to: "For specific timeline questions, I recommend speaking with one of our lawyers. Let me connect you."

**Visual Nodes Impact:**
→ ValidationNode shows: "3 regras" (3 validation rules)

THE LANGGRAPH THAT GETS GENERATED
----------------------------------

## Dynamic State Schema (Per-Agent)

**Each agent gets its own StateGraph** with a dynamically generated schema based on `response_schema`.

**Graph Factory Function:**
```python
def create_agent_state(agent_id: str, response_schema: dict):
    """
    Dynamically creates TypedDict from agent's response_schema.

    Example response_schema:
    {
        "urgency": ["normal", "urgent", "emergency"],
        "issue_type": ["question", "booking", "emergency"],
        "location_preference": ["location_1", "location_2", "location_3", "any"]
    }
    """
    # Core fields (always present)
    fields = {
        "messages": List[Message],  # Required by LangGraph
    }

    # Add agent-specific fields from response_schema
    for field_name in response_schema.keys():
        fields[field_name] = Optional[str]  # All tracking fields are optional strings

    # Dynamically create TypedDict class
    StateClass = TypedDict(f'AgentState_{agent_id}', fields)
    return StateClass


def create_graph_for_agent(agent_config):
    """Creates a compiled graph instance for a specific agent."""
    # 1. Generate state schema
    StateClass = create_agent_state(agent_config.id, agent_config.response_schema)

    # 2. Build graph with fixed pipeline
    graph = StateGraph(StateClass)

    # Add nodes (same for all agents)
    graph.add_node("extract_state", extract_state_node)
    graph.add_node("apply_gating", apply_gating_node)
    graph.add_node("rag_search", rag_search_node)
    graph.add_node("generate_response", generate_response_node)
    graph.add_node("validate", validate_node)
    graph.add_node("handoff", handoff_node)
    # Tools added conditionally based on agent_config.tools

    # Add edges (same for all agents)
    graph.add_edge("extract_state", "apply_gating")
    graph.add_edge("apply_gating", "rag_search")
    graph.add_edge("rag_search", "generate_response")
    graph.add_edge("generate_response", "validate")

    # Conditional edges (rules from agent_config)
    graph.add_conditional_edges("validate", route_after_validation)

    # 3. Compile with checkpointer
    checkpointer = PostgresCheckpointer(connection_string)
    return graph.compile(checkpointer=checkpointer)
```

**Runtime Management:**
```python
# Cache of compiled graphs per agent
compiled_graphs: Dict[str, CompiledGraph] = {}

def get_graph_for_agent(agent_id: str):
    """Gets or creates compiled graph for agent."""
    if agent_id not in compiled_graphs:
        agent = db.get_agent(agent_id)
        compiled_graphs[agent_id] = create_graph_for_agent(agent)
    return compiled_graphs[agent_id]

def update_agent_schema(agent_id: str, new_response_schema: dict):
    """Updates agent's schema and rebuilds graph."""
    # 1. Update database
    agent = db.get_agent(agent_id)
    agent.response_schema = new_response_schema
    db.save(agent)

    # 2. Rebuild graph with new schema
    compiled_graphs[agent_id] = create_graph_for_agent(agent)

    # Note: Existing conversations keep old schema (checkpointed state)
    # New conversations use new schema
```

**Example Generated State (Dental Clinic):**
```python
AgentState_17 = TypedDict('AgentState_17', {
    'messages': List[Message],
    'urgency': Optional[str],
    'issue_type': Optional[str],
    'location_preference': Optional[str]
})
```

**Result:**
- User adds tracking field in UI → Updates `response_schema` in DB → Graph rebuilds
- Fully flexible: any field can be tracked
- No hardcoded universal schema
- Each agent has exactly the fields it needs

KEY PRINCIPLES
--------------

1. **Users talk, we implement** - No graph building, just conversation
2. **One graph structure, dynamic schema** - Fixed pipeline nodes, per-agent state fields
3. **State drives everything** - Schema fields control flow, extracted every turn
4. **Dynamic schema generation** - TypedDict created from response_schema at runtime
5. **Graph factory pattern** - Each agent gets compiled graph instance, cached in memory
6. **Schema updates rebuild graph** - UI changes trigger graph regeneration
7. **Gating = smart filtering** - Show/hide knowledge based on state
8. **Tools as needed** - Model decides when to call
9. **Handoffs for humans** - AI knows its limits
10. **Visual = educational** - Nodes help understand, not build
11. **LangGraph under hood** - All complexity abstracted

Users get a WhatsApp assistant in 20 minutes.
We get enterprise-grade orchestration with LangGraph.
Each agent tracks exactly what it needs, no universal schema limitations.
Win-win.
