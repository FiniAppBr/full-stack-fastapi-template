ConnectAI - Proposed ReAct Architecture
=======================================

This document outlines the clean architecture for the ReAct-based agent system,
designed for full customization, state visibility, and extensibility.


DESIGN PRINCIPLES
-----------------
1. Everything is data, not code - Stages, state fields, gating rules are JSON configs
2. Composition over inheritance - Prompts composed from parts, tools composed per agent
3. Optional complexity - Simple agents don't need stages, power users can enable everything
4. API for everything - Any UI feature should have a corresponding API
5. Builder AI is separate - It generates configs, doesn't touch the runtime


ARCHITECTURE LAYERS
-------------------

  Layer 4: ADVANCED (Power Users)
  ├── Custom gating rules (if X then exclude Y)
  ├── Custom validation rules (never say X, always include Y)
  ├── Webhook tools (call my API when Z happens)
  ├── Custom state fields to track
  └── Custom conversation stages

  Layer 3: BUSINESS CONFIG (Every User)
  ├── Business description → system prompt
  ├── Tone: professional | friendly | energetic
  ├── Emojis: yes | no | minimal
  ├── Language: pt | en | both
  ├── Handoff triggers: [anger, complexity, legal_question, complaint]
  ├── Knowledge: uploaded PDFs, price lists, FAQs
  └── Connected services: Google Calendar, Calendly, etc.

  Layer 2: TOOL LIBRARY (Platform-Provided, User-Enabled)
  │
  │ Built-in (no integration needed):
  ├── search_knowledge    - Always ON (uses their uploaded docs)
  ├── check_calendar      - Internal calendar availability
  ├── book_calendar       - Book on internal calendar
  ├── cancel_booking      - Cancel internal booking
  ├── create_task         - Create kanban task (lead tracking, follow-ups)
  ├── update_task         - Update kanban task status
  ├── send_document       - IF documents uploaded
  ├── collect_lead_info   - ON/OFF toggle
  ├── handoff_to_human    - Always available
  └── flag_urgent         - Always available
  │
  │ External (requires integration - STUBBED):
  ├── google_calendar     - Sync with Google Calendar
  ├── calendly            - Calendly integration
  └── slack_notify        - Send Slack notifications

  Layer 1: PLATFORM (Hardcoded by Us)
  ├── ReAct agent loop
  ├── Tool execution infrastructure
  ├── Checkpointer (state persistence)
  ├── Integration adapters (Google Calendar API, Calendly API, etc.)
  ├── Safety guardrails
  ├── State extraction logic
  └── Multi-turn message splitting


FOLDER STRUCTURE
----------------

Design principles applied:
- SRP (Single Responsibility): Split when different reasons to change
- Cohesion: Keep coupled logic together
- YAGNI: Don't split until needed
- Open/Closed: Easy to extend without modifying

DATA MODELS
-----------

Agent Model (with full customization):

  class Agent(SQLModel):
      id: int
      name: str

      # Identity
      business_description: str      # Main system prompt content
      tone: str                       # "professional" | "friendly" | "energetic"
      language: str                   # "pt" | "en" | "both"
      emoji_usage: str                # "none" | "minimal" | "frequent"

      # State Schema (user-defined fields to track)
      state_schema: dict
      # Example:
      # {
      #   "budget_range": {
      #     "type": "enum",
      #     "options": ["unknown", "low", "medium", "high"],
      #     "description": "Customer's budget range",
      #     "extract_from": "conversation"
      #   },
      #   "customer_name": {
      #     "type": "string",
      #     "description": "Customer's name if mentioned"
      #   },
      #   "interested_products": {
      #     "type": "list",
      #     "description": "Products customer showed interest in"
      #   },
      #   "appointment_booked": {
      #     "type": "boolean",
      #     "description": "Whether an appointment was scheduled"
      #   }
      # }

      # Stages (optional conversation flow)
      stages_enabled: bool
      stages: list[ConversationStage]  # See ConversationStage model below

      # Tools
      enabled_tools: list[str]        # ["search_knowledge", "book_appointment"]
      tool_configs: dict
      # Example:
      # {
      #   "calendar": {
      #     "provider": "google",
      #     "calendar_id": "...",
      #     "credentials_encrypted": "..."
      #   },
      #   "handoff": {
      #     "method": "slack",
      #     "channel": "#support"
      #   }
      # }

      # Handoff
      handoff_triggers: list[str]     # ["anger", "complaint", "legal_question"]

      # Advanced rules
      gating_rules: list[dict]        # Pre-agent filters
      validation_rules: list[dict]    # Post-agent checks

      # Multi-message
      multi_turn_enabled: bool
      multi_turn_config: dict         # {"max_splits": 4, "style": "medium"}

      # Knowledge
      knowledge_blocks: list[Block]   # Related knowledge blocks


Stage Model:

  class ConversationStage(BaseModel):
      id: str                         # "discovery"
      name: str                       # "Discovery Stage"
      goal: str                       # "Understand customer needs"
      instructions: str               # Detailed instructions for LLM
      example_lines: list[str]        # Suggested phrases
      allowed_topics: list[str]       # What can be discussed
      blocked_topics: list[str]       # What cannot be discussed yet
      transition_when: list[str]      # Conditions to move forward
      rag_tags: list[str]             # Only search knowledge with these tags
      next_stage: str | None          # Next stage ID or None if final

CONTEXT EFFICIENCY
------------------

Problem: Stages + RAG + tools + history = context explosion

Solutions:

1. Summarize Old Messages
   - Keep last 4-6 messages in full
   - Summarize earlier messages into "conversation_summary" field
   - Checkpointer stores summary, not full history

2. State IS Memory
   - Extract important info to state fields
   - Don't keep "10 messages discussing budget"
   - Keep "budget_range: medium"

3. Stage-Scoped RAG
   - Each stage has rag_tags
   - Only search knowledge matching current stage tags
   - Discovery stage: ["products", "categories"]
   - Pricing stage: ["pricing", "promotions", "payment_options"]

4. Lazy Tool Calls
   - ReAct naturally does this
   - Agent only calls tools when it decides it needs them
   - Simple greetings = 1 LLM call, no tools


ERROR HANDLING
--------------

1. Tool Failures
   - Retry once with exponential backoff
   - On second failure: graceful degradation
     - Calendar unavailable → "Let me check with my team and get back to you"
     - RAG unavailable → respond without knowledge context
   - Log error, flag for review

2. LLM Garbage Response
   - Validation node catches: empty response, response in wrong language,
     prohibited content, response too long
   - On failure: request regeneration (max 2 retries)
   - After retries: return safe fallback + flag for review

3. Timeout Handling
   - Tool timeout: 10s default (configurable per tool)
   - LLM timeout: 30s default
   - On timeout: treat as tool failure, apply retry logic

4. State Extraction Failures
   - If extraction LLM fails: keep previous state values
   - Never lose state due to extraction error
   - Log and continue

5. Handoff on Repeated Failures
   - 3+ consecutive errors in same conversation → auto-handoff
   - "I'm having some technical difficulties. Let me connect you with someone."


TOKEN BUDGET
------------

1. Context Limits
   - Max input tokens: 8,000 (configurable per agent)
   - Reserve for response: 2,000 tokens
   - Budget breakdown:
     - System prompt: ~1,500 tokens
     - Stage instructions: ~300 tokens
     - RAG context: ~2,000 tokens
     - Message history: ~3,500 tokens
     - Tool definitions: ~700 tokens

2. Message Summarization
   - Trigger: when message_count > 6 OR history_tokens > 3,500
   - Keep last 4 messages in full
   - Summarize earlier messages into "conversation_summary" state field
   - Summary prompt: "Summarize the key points discussed so far in 2-3 sentences"

3. RAG Token Control
   - Max chunks per query: 3 (configurable)
   - Max tokens per chunk: 500
   - Stage-scoped search reduces irrelevant chunks

4. State vs History Tradeoff
   - Extracted state fields replace need for full history
   - Example: "budget_range: high" replaces 5 messages about budget
   - Aggressive extraction = smaller context = faster + cheaper


STAGE TEMPLATES
---------------

Pre-built stage flow templates (users pick one, then customize):

1. CONSULTATIVE_SALES (default for sales-focused businesses)
   Stages: Connection → Discovery → Presentation → Objection Handling → Closing → Follow-up
   Best for: High-ticket sales, real estate, courses, consulting
   Key tools: search_knowledge, collect_lead_info, book_appointment
   State fields: lead_quality, budget_range, objections_raised, decision_timeline

2. LEAD_QUALIFICATION (service businesses)
   Stages: Greeting → Need Identification → Budget Check → Timeline Check → Handoff/Schedule
   Best for: Law firms, agencies, B2B services
   Key tools: collect_lead_info, handoff_to_human, book_appointment
   State fields: service_needed, budget_range, urgency_level, qualified

3. CUSTOMER_SUPPORT (support-focused)
   Stages: Greeting → Issue Identification → Solution Search → Resolution → Satisfaction Check
   Best for: Tech support, product support, general inquiries
   Key tools: search_knowledge, handoff_to_human, flag_urgent
   State fields: issue_type, issue_resolved, satisfaction_score, escalated

4. APPOINTMENT_BOOKING (simple scheduling)
   Stages: Greeting → Service Selection → Availability Check → Booking → Confirmation
   Best for: Dental clinics, salons, gyms, photographers
   Key tools: check_availability, book_appointment, cancel_appointment
   State fields: service_selected, preferred_date, appointment_booked, location
