● High-Value Entity Examples

  The goal: Right chunk → Right turn → Right behavior

  User creates entities that fire precisely when needed, not flooding context.

  ---
  Format

  ENTITY: [name]
  FIRES WHEN: [situation]
  GIVES AGENT: [behavior/knowledge]

  ● Validation Analysis

  1. Can we reliably detect these "FIRES WHEN" conditions?

  Categorizing by detection difficulty:

  Easy (keyword/pattern matching)

  - competitor-comparison: user says "Hotmart", "Kiwify", etc
  - refund-request: "reembolso", "devolver", "dinheiro de volta"
  - raw-files-no: "RAW", "arquivos originais"
  - allergy-caution: "alergia", "intolerância", "celíaco"
  - ready-to-close: "como pago", "qual o pix", "me manda o link"
  ✅ 90%+ accuracy achievable

  Medium (pattern + context)

  - past-failure-reframe: "já tentei", "não consegui" + past tense
  - spouse-objection: "marido", "esposa" + "perguntar", "falar com"
  - not-decision-maker: "chefe", "gestor" + permission context
  - already-tried-that: "já fiz isso", "já tentei" in response to suggestion
  ✅ 80%+ accuracy with simple NLU

  Hard (sentiment + state tracking)

  - frustrated-user-detected: requires sentiment analysis
  - tire-kicker-detect: requires multi-turn engagement scoring
  - high-engagement-close-attempt: requires conversation state
  - objection-not-addressed: requires tracking what was/wasn't handled
  ⚠️ 60-70% accuracy, needs robust state machine

  Very Hard (inference required)

  - fear-of-commitment: subtle signals across turns
  - urgency-injection timing: "right moment" is fuzzy
  - drift-correction: what counts as "off-topic"?
  ⚠️ 50-60% accuracy, high false positive risk

  Verdict: ~60% of entities are reliably detectable. The rest need either:
  - Simpler trigger definitions
  - User-configurable thresholds
  - Accept some false positives/negatives

  2. Are these entities things users would actually write?

  Mapping to how users actually talk (from use cases doc):

  | User says                                                      | Maps to entity                    |
  |----------------------------------------------------------------|-----------------------------------|
  | "If someone asks about refunds, explain the 7-day policy"      | refund-request                    |
  | "For anxious pets: reassuring message"                         | pet-anxiety-reassure              |
  | "If someone uses angry words, hand off to human"               | frustrated-user-detected          |
  | "If budget is under $200, politely explain"                    | budget-disqualify                 |
  | "For people who already bought: check if payment went through" | (support flow, not single entity) |

  What users say vs what we designed:

  ✅ Match:
  - Specific situation → specific response (most entities)
  - "Never do X" guardrails
  - "When X, hand off to human"

  ❌ Mismatch:
  - Users say "if someone seems frustrated" - vague
  - Users say "be motivating" - tone, not entity
  - Users describe flows, not atomic triggers ("check payment, send access, basic troubleshooting")

  Verdict: Users think in terms of:
  1. Situations (easy to author) ✅
  2. Responses (easy to author) ✅
  3. Detection logic (they skip this, assume magic) ❌

  We need to provide detection templates. User picks situation from list or describes it, we map to detection logic.

  3. Does each entity justify its existence (high-value moments)?

  High-value test: Would missing this entity cause a lost sale / angry customer / failed support?

  Clearly high-value (miss = bad outcome)

  - past-failure-reframe: miss = user feels unheard, leaves
  - frustrated-user-detected: miss = escalation, churn
  - ready-to-close: miss = lost sale at finish line
  - dental-emergency: miss = patient in pain ignored
  - budget-disqualify: miss = wasted time on bad fit
  - legal-advice-block: miss = liability risk

  Medium-value (helps but not critical)

  - name-collection: nice personalization
  - social-proof-drop: reinforcement
  - timezone-clarify: prevents confusion
  - weekend-context: sets expectations

  Questionable value (maybe over-engineering)

  - evening-hours-urgency: is this really needed?
  - drift-correction: agent should naturally stay on topic
  - silence-reengagement: 2 minutes is arbitrary

  Verdict: ~70% are genuinely high-value. The rest could be:
  - Merged into broader behaviors
  - Made optional/advanced
  - Removed entirely

  ---
  4. Is there overlap that would cause conflicts?

  Potential conflicts found:

  Same trigger, different responses

  User says "é caro":
  - price-justification-roi: justify the value
  - payment-flexibility: offer installments
  - budget-disqualify: politely decline

  Which fires? All three? User confused.

  Solution: Priority + conditions
  budget-disqualify: only if stated budget < threshold
  payment-flexibility: if interested but price is barrier
  price-justification-roi: default for price objection

  Competing goals

  User hesitating:
  - urgency-injection: push to close
  - fear-of-commitment: address the fear gently

  These are opposite approaches.

  Solution: Context-dependent selection or let user choose strategy

  Collection pile-up

  Early conversation:
  - name-collection fires
  - email-collection fires
  - use-case-collection fires
  - company-collection fires

  Agent asks 4 things at once? Terrible UX.

  Solution: Collection queue with pacing rules (1 field per turn max)

  Guardrail vs action conflict

  - discount-authority-block: "can't give discount"
  - urgency-injection: might imply discount possible

  User asks for discount, agent says no, then later implies deal available?

  Solution: Guardrails always override, explicit hierarchy

  Verdict: Overlap is real and needs:
  1. Priority system
  2. Mutual exclusion rules
  3. Pacing/throttling
  4. Clear hierarchy (guardrails > proactive > reactive)

  ---
  What This Tells Us

  The entity concept is valid but needs:

  1. Detection templates - users pick from menu, not write regex
  2. Priority/hierarchy system - guardrails > proactive > reactive > knowledge
  3. Pacing rules - especially for collection, don't flood
  4. Simpler triggers for hard cases - accept lower precision or make explicit

  Revised approach:

  User authors:
  - SITUATION: pick from list or describe
  - RESPONSE: what agent should say/do
  - PRIORITY: how important (high/medium/low)

  System handles:
  - Detection logic
  - Conflict resolution
  - Pacing
  - Merging into context
