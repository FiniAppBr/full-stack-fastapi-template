THE 3-PHASE APPROACH (Detailed)
================================

PHASE 1: Upload (Instant)
--------------------------

Time: <500ms
User sees: "Processing your file..."


PHASE 2: Processing (Background Worker with 7 Sub-Phases)
-----------------------------------------------------------

THE 7 PROCESSING SUB-PHASES:

2a. EXTRACTION
   What: Get raw content from file (text, tables, images)
   Tools: pypdf, python-docx, pandas, pytesseract
   Output: Raw text + structured data (if tables)
   Version: v0.1+

2b. STRUCTURE DETECTION
   What: Understand what kind of data this is
   Tools: GPT-4o-mini (micro-agent with Instructor)
   Output: {"doc_type": "pricing_table|faq|policy|menu|schedule", "entities": [...]}
   Cost: $0.0001 per file
   Version: v0.2+

2c. VALIDATION
   What: Check for errors, missing data, weird formats
   Tools: GPT-4o-mini (micro-agent)
   Output: {"is_complete": bool, "warnings": [...], "errors": [...]}
   Cost: $0.0001 per file
   Version: v0.2+

2d. CONFLICT DETECTION
   What: Compare with existing blocks, find price changes/contradictions
   Tools: GPT-4o-mini (micro-agent)
   Output: {"has_conflicts": bool, "conflicts": [...], "recommendation": "replace|merge|ask_user"}
   Cost: $0.0002 per file
   Version: v0.2+ (CRITICAL for preventing agent contradictions)

2e. NORMALIZATION
   What: Clean text, standardize formats, structure data
   Tools: Custom logic + LLM for complex cases
   Output: {"structured": {...}, "cleaned_text": "..."}
   Version: v0.2+

2f. ENHANCEMENT
   What: Generate 3-5 natural language variants for better semantic search
   Tools: GPT-4o-mini (micro-agent)
   Output: ["A bath for small dogs costs R$60", "Small dog bathing is R$60", ...]
   Cost: $0.0003 per file
   Version: v0.2+ (20-30% retrieval improvement)

2g. STORAGE
   What: Save everything in hybrid format
   Output: {raw_content, structured_data, natural_language, metadata}
   Version: v0.1+

TOTAL COST PER FILE (v0.2): ~$0.0007 (~R$0.004)
TOTAL TIME: 10-30 seconds

```python
# RQ/Celery worker picks up job
def process_knowledge_file(block_id):
    block = get_block(block_id)

    try:
        # 2a. EXTRACTION - Get raw content from file
        file_type = detect_file_type(block.file_path)
        raw_content = extract_content(block.file_path, file_type)
        # Output: {"text": "...", "tables": [...], "metadata": {...}}

        # 2b. STRUCTURE DETECTION - Understand what kind of data (v0.2+)
        structure = detect_structure(raw_content)
        # Output: {"doc_type": "pricing_table", "entities": ["bath", "groom"], ...}

        # 2c. VALIDATION - Check for errors, missing data (v0.2+)
        validation = validate_data(raw_content, structure)
        # Output: {"is_complete": true, "warnings": [], "errors": []}

        # 2d. CONFLICT DETECTION - Compare with existing blocks (v0.2+)
        conflicts = detect_conflicts(raw_content, existing_blocks)
        # Output: {"has_conflicts": true, "conflicts": [...], "recommendation": "ask_user"}

        if conflicts.has_conflicts and conflicts.recommendation == "ask_user":
            # Pause processing, notify user to resolve
            block.status = "needs_review"
            notify_user_conflicts(block.user_id, conflicts)
            return

        # 2e. NORMALIZATION - Clean, format, standardize (v0.2+)
        normalized = normalize_data(raw_content, structure)
        # Output: {"structured": {...}, "cleaned_text": "..."}

        # 2f. ENHANCEMENT - Generate NL variants for better search (v0.2+)
        nl_variants = generate_nl_variants(normalized.structured)
        # Output: ["A bath for small dog costs R$60", "Small dog bathing is R$60", ...]

        # 2g. STORAGE - Save everything
        block.config = {
            "file_name": block.config["file_name"],
            "file_path": block.config["file_path"],

            # Raw extraction
            "raw_content": raw_content.text,

            # Structured data (for exact queries)
            "structured_data": normalized.structured,

            # Natural language variants (for semantic search)
            "natural_language": nl_variants,

            # Metadata
            "metadata": {
                "doc_type": structure.doc_type,
                "validated": validation.is_complete,
                "entities": structure.entities,
                "conflicts_resolved": True,
                "extraction_method": raw_content.metadata.get("extraction_method")
            }
        }

        block.status = "ready"
        db.commit()

        notify_user(block.user_id, f"{block.config['file_name']} is ready!")

    except Exception as e:
        block.status = "failed"
        block.config["error"] = str(e)
        db.commit()
        notify_user(block.user_id, f"Failed to process {block.config['file_name']}")
```

FILE EXTRACTION (The Meat)
===========================

RECOMMENDATION: Use Unstructured.io for all file types ⭐

Why Unstructured.io?
- Handles PDF, DOCX, XLSX, images, HTML in one library
- Better OCR (PaddleOCR, 80+ languages including Portuguese)
- Table extraction with structure (rows, columns, headers)
- Designed for LLM pipelines
- Free and open-source
- 2025 Benchmark: 100% accuracy on simple tables, 75% on complex

ALL File Types (Unified Approach)
----------------------------------
TOOLS: Unstructured.io ⭐

```python
from unstructured.partition.auto import partition

def extract_content(file_path):
    """
    Universal extractor using Unstructured.io
    Handles: PDF, DOCX, XLSX, images, TXT, HTML, and more
    """

    # Auto-detect file type and extract
    # strategy="hi_res" for best table extraction (uses OCR)
    elements = partition(
        filename=file_path,
        strategy="hi_res",  # Use OCR for images/scanned PDFs
        languages=["eng", "por"]  # English + Portuguese
    )

    # Combine all text elements
    text = "\n\n".join([str(el) for el in elements])

    # Extract tables separately (structured data)
    tables = []
    for el in elements:
        if el.category == "Table":
            tables.append({
                "text": str(el),
                "metadata": el.metadata.to_dict()
            })

    return {
        "text": text,
        "tables": tables,
        "metadata": {
            "num_elements": len(elements),
            "has_tables": len(tables) > 0,
            "extraction_method": "unstructured_hi_res"
        }
    }
```

```python
import pandas as pd

def extract_excel(file_path):
    """
    Excel is better handled by pandas for structured data
    Use Unstructured.io for text extraction, pandas for data manipulation
    """
    excel = pd.ExcelFile(file_path)

    sheets = {}
    for sheet_name in excel.sheet_names:
        df = pd.read_excel(excel, sheet_name)
        sheets[sheet_name] = df.to_dict('records')

    # Also generate text version for search
    text = ""
    for sheet_name, rows in sheets.items():
        text += f"\n\n{sheet_name}:\n"
        for row in rows:
            text += " | ".join([f"{k}: {v}" for k, v in row.items()]) + "\n"

    return {
        "text": text,
        "structured": sheets,
        "metadata": {"sheets": len(excel.sheet_names)}
    }
```

SEARCH STRATEGIES (Pick Based on Scale)
========================================

v0.1: PostgreSQL Full-Text Search (0-1000 blocks)
--------------------------------------------------
NO VECTORS. Just use built-in PostgreSQL search.

```python
def search_fulltext(blocks, query):
    # PostgreSQL full-text search
    results = db.execute(
        """
        SELECT
            id,
            config->>'content' as content,
            ts_rank(
                to_tsvector('portuguese', config->>'content'),
                plainto_tsquery('portuguese', :query)
            ) as rank
        FROM block
        WHERE id = ANY(:block_ids)
          AND to_tsvector('portuguese', config->>'content') @@
              plainto_tsquery('portuguese', :query)
        ORDER BY rank DESC
        LIMIT 3
        """,
        {"block_ids": [b.id for b in blocks], "query": query}
    ).fetchall()

    return results
```

PROS: Zero setup, built-in, fast enough
CONS: Not semantic (won't match "haircut" to "men's cut")

---

v0.2: Add Chunking (1000-5000 blocks)
--------------------------------------
Split content into chunks, search chunks instead of full documents.

```python
from langchain.text_splitter import RecursiveCharacterTextSplitter

# On upload, after extraction:
def chunk_content(text):
    splitter = RecursiveCharacterTextSplitter(
        chunk_size=500,
        chunk_overlap=50
    )
    return splitter.split_text(text)

# Store in separate table:
CREATE TABLE knowledge_chunk (
    id SERIAL PRIMARY KEY,
    block_id INTEGER REFERENCES block(id),
    chunk_text TEXT,
    chunk_index INTEGER
);

# Search chunks, not full blocks:
SELECT * FROM knowledge_chunk
WHERE to_tsvector('portuguese', chunk_text) @@ plainto_tsquery('portuguese', :query)
ORDER BY ts_rank(...) DESC
LIMIT 3
```

PROS: More precise results
CONS: More storage, slightly more complex

---

v0.3: Add Vector Search (5000+ blocks or need semantic)
--------------------------------------------------------
Use embeddings + pgvector for semantic search.

```python
from sentence_transformers import SentenceTransformer

# Load model once at startup
model = SentenceTransformer('all-MiniLM-L6-v2')

# On upload, after chunking:
def embed_chunks(chunks):
    return model.encode(chunks)

# Store embeddings:
ALTER TABLE knowledge_chunk ADD COLUMN embedding vector(384);

# Search:
def search_semantic(query, agent_id):
    query_emb = model.encode([query])[0]

    results = db.execute(
        """
        SELECT kc.chunk_text,
               1 - (kc.embedding <=> :query_emb) as similarity
        FROM knowledge_chunk kc
        JOIN block b ON kc.block_id = b.id
        WHERE b.agent_id = :agent_id
        ORDER BY kc.embedding <=> :query_emb
        LIMIT 3
        """,
        {"query_emb": query_emb, "agent_id": agent_id}
    ).fetchall()

    return results
```

PROS: Semantic understanding ("haircut" matches "men's cut")
CONS: Requires compute for embeddings, more complex

---

v1.0: Hybrid Search (Best of Both)
-----------------------------------
Combine full-text + vector search.

```python
def search_hybrid(query, agent_id):
    # 70% semantic, 30% keyword
    results = db.execute(
        """
        SELECT
            chunk_text,
            (0.7 * (1 - (embedding <=> :query_emb)) +
             0.3 * ts_rank(to_tsvector('portuguese', chunk_text),
                           plainto_tsquery('portuguese', :query))
            ) as score
        FROM knowledge_chunk kc
        JOIN block b ON kc.block_id = b.id
        WHERE b.agent_id = :agent_id
        ORDER BY score DESC
        LIMIT 3
        """
    ).fetchall()

    return results
```

PROS: Best accuracy
CONS: Most complex


VERSIONING (Critical - Don't Skip)
===================================

Problem: User uploads menu.pdf, then uploads new menu.pdf
→ Now you have 2 menus with different prices!

Solution: Version tracking + auto-deprecation

```python
# Block schema addition:
{
    "status": "ready" | "processing" | "failed" | "superseded",
    "replaces": null | block_id,  # Points to old version
    "replaced_by": null | block_id  # Points to new version
}

# On upload:
def create_knowledge_block(agent_id, filename):
    # Check if file with same name exists
    old_block = db.query(Block).filter(
        Block.agent_id == agent_id,
        Block.config['file_name'] == filename,
        Block.status == 'ready'
    ).first()

    # Create new block
    new_block = Block(
        agent_id=agent_id,
        config={"file_name": filename, "status": "processing"}
    )

    # Link versions
    if old_block:
        new_block.config["replaces"] = old_block.id
        old_block.status = "superseded"
        old_block.config["replaced_by"] = new_block.id

    db.commit()
    return new_block
```

On search: Only query blocks where status="ready" (excludes superseded)

CRITICAL CONCERNS (Where This Can Fail)

Upload/Processing is BORING (solved tech):

- Save to DB: works

RETRIEVAL is where you WIN OR LOSE.


RETRIEVAL CHALLENGES
====================

Challenge 1: Keyword Mismatch (Semantic Gap)
---------------------------------------------
Customer: "How much for a haircut?"
Knowledge: "Men's cut - R$50"

Problem: "haircut" ≠ "cut" → Full-text search MISSES

PostgreSQL full-text prediction: Will catch ~65-75% of queries
- ✓ Works for exact matches ("price", "hours", "R$80")
- ✗ Fails on semantic matches ("haircut" vs "cut", "cheap" vs "inexpensive")

Solution if accuracy <70%:
→ Add semantic search (embeddings + pgvector) in v0.3


Challenge 2: Buried Information (Noise Problem)
------------------------------------------------
Customer: "What are your hours?"
Knowledge Block: 2000-word PDF... buried on page 3: "Open Tue-Sun 12pm-10pm"

Problem: Full-text finds the document, returns ALL 2000 words
Agent can't extract the answer from noise

Solution:
→ Add chunking in v0.2 (split into 500-char pieces, search chunks not docs)


Challenge 3: Relevance Ranking
-------------------------------
Customer: "How much is a bath?"

BAD ranking (what might happen with naive search):
1. "We offer baths for dogs and cats..." (generic intro)
2. "Bath services are available..." (generic description)
3. "Bath - Medium: R$80" (THE ACTUAL ANSWER)

GOOD ranking (what we need):
1. "Bath - Medium: R$80" (THE ANSWER)
2. "Bath includes shampoo, conditioner, blow dry" (context)
3. "Add nail trim for R$20" (upsell)

Problem: Scoring algorithm matters more than you think

Solution:
→ v0.1: ts_rank (PostgreSQL scoring)
→ v0.3: Cosine similarity (vector scoring)
→ v1.0: Hybrid (combine both scores: 70% semantic + 30% keyword)


Challenge 4: Scale & Speed
---------------------------
Agent has: 50 knowledge blocks × 20 chunks each = 1000 chunks
Customer query arrives
Time budget: <200ms to search all 1000 chunks

Can PostgreSQL full-text handle this?
- 1000 chunks: YES (50-100ms)
- 5000 chunks: MAYBE (100-200ms)
- 10k+ chunks: NO (>500ms, need pgvector indexes)

Solution path:
→ v0.1: PostgreSQL full-text (good for <5000 chunks)
→ v0.3: pgvector with IVFFlat indexes (good for <100k chunks)
→ v1.0: Redis cache for hot queries (<10ms)

```python
def retrieve_knowledge(agent_id: int, query: str):
    """Dead simple PostgreSQL full-text search"""

    results = db.execute("""
        SELECT
            id,
            config->>'file_name' as source,
            config->>'content' as text,
            ts_rank(
                to_tsvector('portuguese', config->>'content'),
                plainto_tsquery('portuguese', :query)
            ) as relevance
        FROM block
        WHERE agent_id = :agent_id
          AND status = 'ready'
          AND to_tsvector('portuguese', config->>'content') @@
              plainto_tsquery('portuguese', :query)
        ORDER BY relevance DESC
        LIMIT 3
    """, {"agent_id": agent_id, "query": query}).fetchall()

    return [
        {
            "text": r.text[:500],  # First 500 chars
            "source": r.source,
            "relevance": r.relevance
        }
        for r in results
    ]
```

BEST-IN-CLASS RETRIEVAL STACK
==============================

For >90% Accuracy:

1. COLBERT v2 or BGE Reranker (Best Accuracy)
   - Not just embeddings, but reranking models
   - Takes top 10 candidates, carefully picks best 3
   - 10-15% accuracy improvement over basic embeddings

2. Cohere Embed v3 Multilingual (Best Embeddings for Portuguese)
   - Better than OpenAI for Portuguese/English
   - 1024 dimensions
   - $0.10 per 1M tokens (cheap)

3. LangChain/LlamaIndex Query Understanding
   - Parse user intent before searching
   - "How much for a medium dog bath?" → Extract: {intent: "pricing", service: "bath", size: "medium"}
   - Route to structured data vs semantic search

4. Hypothetical Document Embeddings (HyDE)
   - Instead of embedding the query directly
   - Have LLM generate what the answer MIGHT look like
   - Embed that, search for similar documents
   - Example:
     Query: "How much for a bath?"
     HyDE: "A bath for a medium dog costs approximately R$80"
     Search for documents similar to that ^ (more accurate)

MICRO-AGENT ARCHITECTURE
========================

Each micro-agent = one focused LLM call with tools.

Agent 1: Structure Detector
----------------------------
```python
from instructor import patch
from openai import OpenAI

client = patch(OpenAI())

class DocumentStructure(BaseModel):
    doc_type: str  # "pricing_table" | "faq" | "policy_doc" | "menu" | "schedule"
    columns: list[str]
    entities: list[str]  # Services, products, policies mentioned
    confidence: float

def detect_structure(content: str) -> DocumentStructure:
    return client.chat.completions.create(
        model="gpt-4o-mini",  # Cheap, fast
        response_model=DocumentStructure,
        messages=[{
            "role": "user",
            "content": f"Analyze this document structure:\n\n{content}"
        }]
    )
```

Cost: $0.0001 per document (negligible)
Benefit: Know HOW to process the file

WHY MICRO-AGENTS HELP
=====================

1. BETTER DATA QUALITY
   - Structured + validated before storage
   - Conflicts detected early
   - Missing data flagged

2. BETTER RETRIEVAL
   - Natural language variants improve semantic search hit rate
   - Structured data enables exact queries
   - Metadata helps routing (pricing query → search pricing blocks first)

3. LOWER TOKENS AT QUERY TIME
   - Clean, normalized data = shorter, clearer chunks
   - No need for agent to parse messy data
   - Example:
     Without: Agent gets raw "Bath Small R$60 Medium R$80 Large R$100"
     With: Agent gets structured {"service": "bath", "small": 60, "medium": 80, "large": 100}
     Saves ~40% tokens in prompt

4. USER TRUST
   - "Found conflict: bath price R$55 vs R$60. Which is correct?"
   - User fixes → clean data → better answers → trust
