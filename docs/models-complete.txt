FINAL ARCHITECTURE:
-------------------

1. Agent Model (app/models/agent.py)
   - Represents a configured AI agent
   - Foreign key to User (owner_id)
   - Fields: name, description, is_active, is_published, timestamps

2. Block Model (app/models/block.py)
   - Single table for ALL block types
   - Discriminator field: block_type (knowledge, personality, action)
   - All type-specific fields in one table (nullable where not used)

3. User Model (app/models/user.py)
   - Existing authentication model
   - Unchanged

DATABASE SCHEMA:
----------------

Table: agent
- id (primary key)
- owner_id (FK to user.id, UUID)
- name, description
- is_active, is_published
- whatsapp_number, webhook_url (for future integrations)
- created_at, updated_at, published_at

Table: blocks
- id (primary key)
- agent_id (FK to agent.id)
- block_type (knowledge | personality | action)
- name, description, is_active
- created_at, updated_at

Knowledge fields:
- content, content_type, file_path, file_type

Personality fields:
- tone, languages, use_emojis, emoji_frequency, response_length
- constraints, guidelines, example_conversations (JSON)

Action fields:
- action_type, config (JSON), integration_id
- trigger_conditions, requires_confirmation

Shared:
- metadata_ (JSON)

DESIGN DECISIONS:
-----------------

✅ Single-table inheritance (composition pattern)
   - One blocks table with discriminator column
   - All block types share same table
   - Type-specific validation done via Pydantic schemas (API layer)

✅ Why this approach:
   - Simpler migrations (no JOIN complexities)
   - Plays to SQLModel's strengths (Pydantic integration)
   - Fast queries (no JOINs needed)
   - Easy to add new block types (just add columns)
   - Flexible metadata field for future extensions

✅ What we avoided:
   - Polymorphic inheritance with child tables (SQLModel limitations)
   - Pure SQLAlchemy (unnecessary complexity for our needs)
   - Joined-table inheritance (migration headaches)

LESSONS LEARNED:
----------------

1. SQLModel is great for simple CRUD, awkward for complex inheritance
2. Composition > inheritance for our use case
3. Pydantic validation at API layer > database constraints
4. Single-table with discriminator is simpler than joined tables
5. Don't over-engineer v0.1 - ship simple, iterate based on real needs
