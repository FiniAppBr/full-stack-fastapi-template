PART 1: WHAT WE'RE BUILDING
═══════════════════════════════════════════════════════════════════════════════

THE VISION:
-----------
AI customer service platform that non-technical business owners can configure
in under 10 minutes via conversational interface.

THE PROBLEM:
------------
Small businesses (restaurants, salons, law firms, gyms) get overwhelmed by
customer messages on WhatsApp/Instagram. They can't afford human support 24/7.

Existing solutions suck:
- Traditional chatbot builders: Complex flowcharts, takes hours to learn
- AI solutions: Too generic (ChatGPT), not business-specific
- Hiring VAs: Expensive, hard to scale

THE SOLUTION:
-------------
**Builder AI**: Chat interface where AI helps you configure your customer agent
**Blocks System**: Behind-the-scenes structure (knowledge, personality, actions)
**Customer Agent**: The AI that actually talks to your customers

KEY INSIGHT: Business owners don't want to "design" AI behavior.
They want to answer questions and have it work.

PART 2: THE INTERFACE (Builder AI Concept)
═══════════════════════════════════════════════════════════════════════════════

SPLIT-SCREEN LAYOUT:
--------------------
LEFT: Block list (the configuration) - Notion-style, collapsible sections
RIGHT: Chat with Builder AI - conversational setup assistant

USER FLOW (Example: Restaurant owner):
---------------------------------------
1. Opens app, clicks "Create New Agent"
2. Builder AI: "Hi! Tell me about your business"
3. User: "Italian restaurant, want to handle reservations and menu questions"
4. Builder AI: "Great! Can you share your menu?"
5. [User drags menu.pdf into chat]
6. Builder AI: "✓ Got it! Found 45 items. Added to your knowledge base →"
   [Menu block appears on left]
7. Builder AI: "How about reservations - do you use Google Calendar?"
8. User: "Yes"
9. Builder AI: "Click here to connect: [Connect]"
   [User connects, Reservations block appears on left]
10. Builder AI: "What tone should your AI use?"
11. User: "Friendly and warm"
12. Builder AI: "✓ Set to friendly mode"
    [Personality block appears on left]
13. Builder AI: "Ready to test it?"

TOTAL TIME: 5 minutes
TOTAL EFFORT: Answered 3 questions, dropped 1 file, clicked 1 OAuth button

BLOCKS CREATED AUTOMATICALLY:
- 📋 Knowledge: Menu (45 items)
- 📅 Action: Reservations (Google Calendar)
- 🎭 Personality: Friendly & warm

WHY THIS WORKS:
---------------
✓ Conversational (not forms)
✓ AI guides you (suggests best practices)
✓ Visual feedback (blocks appear in real-time)
✓ Flexible (can edit blocks manually if you want)
✓ Fast (typical setup: 3-10 minutes)

PART 3: WHAT WE BUILD (The 20%)
═══════════════════════════════════════════════════════════════════════════════

WHAT EXISTING TOOLS SOLVE (80%):
---------------------------------
✓ RAG infrastructure (LangChain, pgvector)
✓ LLM calling (OpenAI SDK, function calling)
✓ State management (Temporal, LangGraph)
✓ Basic integrations (Google Calendar API, Stripe)

WHAT WE MUST BUILD (20% - Our Moat):
-------------------------------------
1. BLOCKS → AGENT TRANSLATION
   How to read our blocks and generate prompts/tools/constraints
   Example: "Never give legal advice" → specific prompt engineering

2. BUSINESS-SPECIFIC INTEGRATIONS
   Custom connectors for each business's unique setup
   Example: Restaurant's Google Sheet with specific column structure

3. QUALITY CONTROL & SAFETY
   Business-specific validation ("friendly but not pushy")
   Edge case handling ("book tomorrow" at 11:55 PM)

4. MULTI-BLOCK REASONING
   Which blocks to use when (orchestration logic)
   Example: Free trial block + pricing block → when to mention which?

5. PERSONALITY NUANCE
   Capture specific tone per business
   Example: "Professional but warm" vs "Professional but authoritative"

6. INTELLIGENT ANALYTICS
   Why is escalation rate high? Missing knowledge? Wrong tone?
   Suggest specific improvements

7. BUILDER AI INTERFACE ★ BIGGEST MOAT
   The entire "chat to build your AI" experience
   No competitor has this (they all use forms/flowcharts)

8. ERROR RECOVERY
   Handle weird customer behavior
   Fallback logic for edge cases

SUMMARY: Tools commoditize infrastructure. We differentiate on UX and business logic.

✅ Backend: FastAPI + Python 3.11 + SQLModel
✅ Database: PostgreSQL (with pgvector for embeddings)
✅ Auth: JWT tokens
✅ Deployment: systemd services on Ubuntu server (195.35.43.23)
   - Frontend: port 5459
   - Backend: port 5460

WHAT WE NEED TO ADD:
--------------------
⚙️ Temporal (orchestration, durability, visibility)
⚙️ LangChain (RAG infrastructure)
⚙️ LangGraph (multi-agent workflows)
⚙️ Mem0 (long-term memory across sessions)
⚙️ Gemini Flash 2.0/2.5 (primary LLMs - free tier!)
⚙️ Instructor (structured outputs from LLMs)

TWO AI SYSTEMS:
---------------
1. BUILDER AI (helps user configure)
   - Temporal workflow: BuilderAIWorkflow
   - Activities: detect_intent, create_blocks, generate_response
   - Model: Gemini Flash 2.0 (cheap, fast)
   - Tools: BlockCreator, FileParser, IntegrationManager

2. CUSTOMER AGENT (talks to end customers)
   - Temporal workflow: CustomerAgentWorkflow
   - Activities: classify_intent, retrieve_knowledge, execute_action
   - Models: Multi-model routing (Flash 2.0 → 2.5 → GPT-4 for critical)
   - Tools: Read knowledge blocks, book appointments, send emails


TEMPORAL ARCHITECTURE (Production-Validated Patterns):
-------------------------------------------------------
Based on real production insights from companies with thousands of users.

KEY PATTERN: Microagents (not monolith)
----------------------------------------
❌ DON'T: One big agent doing everything (unreliable, 60% hallucination rate)
✅ DO: Each agent = one Temporal activity with focused task

BUILDER AI WORKFLOW STRUCTURE:
```
BuilderAIWorkflow (orchestration)
  ├─ detect_intent_agent (activity)         → Gemini Flash 2.0
  ├─ generate_response_agent (activity)     → Gemini Flash 2.0
  ├─ create_blocks_agent (activity)         → Gemini Flash 2.5
  ├─ summarize_conversation (activity)      → Triggered after 30 turns
  └─ save_blocks_to_db (activity)

Pattern: Digital Twin
- One workflow per business configuration session
- Workflow ID: builder-ai-{business_id}-{session_id}
- Isolated context (no data leaks)
```

CUSTOMER AGENT WORKFLOW STRUCTURE:
```
CustomerAgentWorkflow (orchestration)
  ├─ classify_customer_intent (activity)    → Gemini Flash 2.0
  ├─ retrieve_knowledge (activity)          → RAG with pgvector
  ├─ generate_customer_response (activity)  → Gemini Flash 2.5
  ├─ execute_action (activity)              → API calls (calendar, payment)
  └─ save_to_mem0 (activity)                → Long-term memory

Pattern: Digital Twin
- One workflow per customer conversation
- Workflow ID: customer-agent-{business_id}-{customer_id}-{session_id}
```

TEMPORAL BENEFITS:
------------------
✅ Durability: Conversation survives crashes/restarts
✅ Visibility: See input/output of every agent in UI
✅ Queries: Inspect agent state mid-conversation
✅ Signals: User input without polling
✅ Timers: Cleanup during idle (summarize after 3 min idle)
✅ Continue-as-new: Summarize long conversations, start fresh workflow
✅ Retries: Automatic retry with exponential backoff

CONTEXT MANAGEMENT:
-------------------
RULES:
1. Activities load only what they need (not full conversation history)
2. Workflow holds only "durable shared state"
3. Return values from activities are minimal
4. Summarize after 25-30 turns (Builder AI) or 20-25 (Customer Agent)

EXAMPLE - What to store in workflow state:
✅ created_blocks: List[Block]
✅ business_context: Dict[str, Any]
✅ conversation_summary: str (compressed)

❌ DON'T store:
❌ Full conversation history (too big)
❌ Uploaded file contents (store in S3, keep references)
❌ LLM reasoning traces (ephemeral, only in activities)

COST OPTIMIZATION (Multi-Model Routing):
-----------------------------------------
Simple tasks (80%) → Gemini Flash 2.0 (FREE tier)
Complex tasks (15%) → Gemini Flash 2.5 (~$0.01/1M tokens)
Critical tasks (5%) → GPT-4o-mini or Claude 3.5 Sonnet

Each activity can use different model!

Example:
- detect_intent_agent → Flash 2.0
- create_blocks_agent → Flash 2.5 (needs structured extraction)
- validate_blocks_agent → GPT-4o-mini (critical validation)

ESTIMATED COSTS:
----------------
Builder AI session (30 turns): ~$0.02
Customer conversation (20 turns): ~$0.01
Using Gemini Flash 2.0 for 80% of calls = 90% cost savings

DATABASE SCHEMA (Simplified):
------------------------------
User
  └── Business
       └── Agent
            ├── Blocks (polymorphic)
            │    ├── KnowledgeBlock (text, file, FAQ)
            │    ├── PersonalityBlock (tone, language, emoji_usage)
            │    ├── ActionBlock (appointment, payment, form)
            │    ├── IntegrationBlock (calendar, email, WhatsApp)
            │    └── HandoffBlock (escalation rules)
            ├── BuilderConversations (chat with Builder AI)
            └── CustomerConversations (customer interactions)

PART 6: TECHNICAL SETUP (Next Actions)
═══════════════════════════════════════════════════════════════════════════════

IMMEDIATE SETUP (Before coding):
---------------------------------

1. INSTALL TEMPORAL (30 minutes):
   ```bash
   # Create Temporal database
   psql -U connectai -c "CREATE DATABASE temporal;"

   # Install Temporal CLI
   curl -sSf https://temporal.download/cli.sh | sh

   # Run Temporal server
   temporal server start-dev --db-filename /opt/temporal/temporal.db

   # Temporal UI will be on http://localhost:8080
   ```

2. INSTALL PYTHON DEPENDENCIES:
   ```bash
   cd /opt/connectai/backend
   pip install temporalio langchain langchain-google-genai \
               langchain-postgres instructor mem0ai
   ```

3. ADD GEMINI API KEY:
   - Get free API key from https://aistudio.google.com/apikey
   - Add to /opt/connectai/.env:
     ```
     GEMINI_API_KEY=your_key_here
     ```

4. CREATE FEATURE BRANCH:
   ```bash
   git checkout -b feature/builder-ai-v0.1
   ```

5. DATABASE MIGRATIONS:
   ```bash
   # Add Block models
   cd backend
   alembic revision --autogenerate -m "Add blocks system"
   alembic upgrade head
   ```


DEVELOPMENT WORKFLOW:
---------------------
1. Work in feature branch: feature/builder-ai-v0.1
2. Build end-to-end skeleton first (wire everything together)
3. Then add sophistication
4. Deploy to staging early, test frequently
5. Don't perfectionism - ship messy v0.1, iterate fast

PART 7: KEY DECISIONS & PRINCIPLES
═══════════════════════════════════════════════════════════════════════════════

CORE PRINCIPLES:
----------------
1. **Speed over perfection**: Get v0.1 working in 2 weeks, iterate
2. **User feedback first**: Build → Test → Learn → Iterate
3. **Don't over-engineer**: Use simple solutions, upgrade when needed
4. **Microagents, not monoliths**: One focused task per agent
5. **Cost-conscious**: Gemini Flash for 80%, expensive models for 5%
6. **Temporal for everything durable**: Conversations, workflows, state
7. **Visibility matters**: Queries, logs, debugging tools from day 1

DESIGN DECISIONS:
-----------------
✅ Chat interface (not forms) - more engaging, guided
✅ Blocks abstraction (not flowcharts) - simpler mental model
✅ Builder AI (not pure manual config) - our moat
✅ Temporal (not custom orchestration) - production-proven
✅ Gemini Flash (not GPT-4) - cost optimization
✅ Multi-model routing (not single model) - reliability + cost
✅ PostgreSQL (not separate vector DB yet) - pgvector is enough for v0.1

WHAT TO AVOID:
--------------
❌ Flowchart builders (complex, intimidating)
❌ One mega-agent (unreliable, expensive)
❌ Pure prompt-based (no structure, unpredictable)
❌ Over-engineering v0.1 (prove concept first)
❌ Custom infrastructure (use Temporal, don't reinvent)

PART 9: RISKS & MITIGATION
═══════════════════════════════════════════════════════════════════════════════

RISK 1: Builder AI conversation is awkward
→ Start with hardcoded flow, upgrade to LLM
→ Can always fall back to manual block adding

RISK 2: Customer agent quality is poor
→ This is the hardest part (expect this)
→ Use production patterns from Temporal webinar
→ Extensive testing with real conversations
→ Iterate on prompts, add guardrails

RISK 3: Setup takes too long (>10 min)
→ Builder AI needs to be smarter
→ Add templates for common industries
→ Pre-fill intelligent defaults

RISK 4: Integration complexity
→ Start with 1-2 integrations (Google Calendar, WhatsApp)
→ Add more based on demand
→ Use existing libraries (not custom)

RISK 5: Costs too high (LLM usage)
→ Multi-model routing (Flash 2.0 for 80%)
→ Caching (Anthropic prompt caching, 90% savings)
→ Summarization (reduce context size)
→ Monitor costs closely

RISK 6: Users don't trust AI-generated config
→ Show blocks in real-time (transparency)
→ Allow manual editing
→ Test mode before going live

RISK 7: Takes longer than expected
→ Cut scope aggressively
→ Focus on core flow
→ Ugly but functional is fine for v0.1
